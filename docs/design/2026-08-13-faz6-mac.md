# Phase 6 — Mac app: runner bridge + SwiftUI skeleton (2026-08-13)

Scope: K7 (Mac client + runner in a single bundle), K2 (server bots are unaffected while the Mac
is off), K15/K18 (the engine's single tool surface is MCP). This document records the phase's
five core decisions and the live evidence.

## 1. Transport split: MCP only at the engine boundary, WebSocket to the runner

The Claude Code ↔ Go boundary is MCP (Streamable HTTP, `/mcp/mac`); the Go ↔ Swift runner
boundary, on the other hand, is plain WebSocket (`/api/runner/ws`, JSON text frames:
`hello` / `call` / `result`). Making the runner speak MCP would stack two MCP servers on top of
each other, whereas all the runner needs is "declare tools, receive calls, return results". The
wire protocol is our contract, but unknown frames are ignored on the Swift side (and on the Go
side too) — both directions survive version skips. The connection always goes Mac→server
(outbound): no port is opened on the Mac, no NAT/firewall hassle (K7).

## 2. Dynamic tool surface: "present when connected, absent when not" (K2)

`gateway.NewDynamic(source)` reads the source on every `tools/list` and `tools/call`;
`runner.Hub` returns an EMPTY list when no session is connected. The engine never sees the
tools → doesn't attempt local work → server bots keep flowing as before. Queuing/compensation is
deliberately ABSENT (K7 scope decision): while the Mac is off, local file work becomes
"impossible", and the bot explains this with a handoff card (`ErrNotConnected` reaches the model
as a tool error).

**Live evidence (on this machine):** core up, `tools/list` → `[]`; Swift
`URLSessionWebSocketTask` connected and sent hello → 2 tools in the list; `tools/call
read_file` → the file contents came back from the Swift process as an MCP result; once the
process was killed the list was `[]` again. On the Go side the same loop is pinned down by
`TestDynamicGatewayEmptyToolsList` + 7 hub tests.

## 3. Class map: static set, dynamic availability

The orchestrator's `ToolClasses` map is built at startup and does not change during a run; the
runner's tool SET is fixed (`runner.StaticClasses`:
`mcp__mac__read_file`/`list_dir` → read, `write_file`/`trash_item` → write),
and only availability changes. Local reads do NOT taint (§5.1 is about external content);
`trash_item` is reversible but still write class — it goes through the approval gate. The Google
gateway classes are MERGED into the same map (an overwrite bug was caught and fixed in this
phase). An unknown class name in the runner's declaration is treated as `external`, the safe
side; `execute` can never get a rule.

## 4. Local policy floor: the server can only narrow

`LocalPolicy` is the runner's own floor: a root allowlist (Documents / Desktop / Downloads), a
local NSAlert confirmation for the write class, a 512 KB read limit. Whatever the server's
approval gate says, this floor does not loosen (K security: the server narrows, it cannot widen).

Field lesson: `URL.resolvingSymlinksInPath` does NOT resolve intermediate symlinks when the path
DOES NOT EXIST (verified live) — for a new file write, that means a symlink escape out of the
root. Fix: go to the deepest existing ancestor, resolve it, and re-append the non-existent tail
(`LocalPolicy.canonicalize`). A test we wrote caught this hole; a concrete payoff of the
"tests + type safety" expectation.

## 5. Swift package: SPM skeleton first, .app packaging later

`mac/` is a dependency-free SPM package (Swift 6 strict concurrency, macOS 14+, proven with
`swift build` + `swift test`, 15 tests). No external library for WebSocket —
`URLSessionWebSocketTask` is enough (live compatibility with coder/websocket proven). The UI is a
functional skeleton of the three-column shell from the design handoff package (272px sidebar,
bot avatar gradients, Approval Center badge, `MenuBarExtra`); pixel polish will follow the design
file. Developer ID signing + notarization is waiting on an Apple Developer membership (an open
user decision) — until then the app runs locally with `swift run`; since TCC permissions will be
tied to the bundle identity, the signing step will come together with .app packaging.
There is deliberately no Swift job in CI: macOS runners are costly, the local `swift test` is
documented (Linux CI runs Go).

## 6. Keep-alive: ping (added 2026-08-15)

In production the connection dropped every two minutes. The cause was not on our side: while the
connection is idle (the user isn't typing) no frames flow at all, and the reverse proxy in
between (Cloudflare) closed the idle WebSocket after ~100 seconds. The result was more than log
noise — for the duration of the disconnect `GatewayTools()` returned empty, meaning the bot did
NOT see the Mac tools AT ALL (the "present when connected" side of K2 was being lost by
accident).

The fix is a two-way ping: on the Go side `Hub.canliTut` sends a `conn.Ping` every 30 seconds
(as the library requires, it runs alongside the read loop, which is what reads the pong) and
drops the session if it goes unanswered. The Swift side also pings at the same interval — so
that `receive()` doesn't hang forever if the server or the network dies silently. The
callback-based `sendPing` in Swift is a deliberate choice: the async wrapper leaves the
continuation hanging if the pong never arrives, and task cancellation can't wake it either. TCP
keepalive can't be relied on: the proxy can keep TCP alive while closing the WebSocket.
